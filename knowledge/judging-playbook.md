# Judging playbook — how hackathon projects actually get scored

Use with the event's own criteria in `brief/problem.md`. When the event doesn't publish weights, assume the common set below.

## The usual criteria and what full marks looks like

| Criterion (typical weight) | Scores low | Scores full marks |
|---|---|---|
| **Innovation / originality** (20–30%) | The obvious idea for the problem statement (chatbot, dashboard, "Uber for X") | A specific angle nobody else took; judges say "I hadn't thought of that" |
| **Technical complexity / implementation** (20–30%) | Slides, Figma, hard-coded screens, "AI" that is an if-statement | A working end-to-end flow on real input, with one genuinely hard part (AI on images/voice, real-time, maps, a non-trivial algorithm) and you can explain it |
| **Impact / usefulness** (20–25%) | "This will help everyone" | One named user, one painful problem, one number (with source) showing size, and a believable path to use |
| **Design / UX** (10–20%) | Default styling, blank states, broken on mobile | Looks like a real product; the core flow takes ≤3 taps; loading and error states exist |
| **Presentation / pitch** (10–15%) | Reading slides, demo fails, runs over time | Problem in one sentence, wow by 0:45, ends on impact, on time, handles questions honestly |
| **Sponsor track fit** (separate prize) | Sponsor's tool mentioned only on a slide | Sponsor's API/tool is central to the demo moment |

## How judging really happens (and what to do about it)
- Judges see **30–80 projects**, often 3–5 minutes each, often tired. They decide in the **first 30 seconds** whether you're a contender. → Open with the problem in one human sentence and show the product immediately.
- They score **what they see working**, not what you describe. → One flow that works beats five half-features.
- They **ask "is this real?"** about data and AI. → Label demo data honestly; be ready to show which part is AI.
- They **compare you to the obvious idea**. → Name the obvious approach and say in one line why yours is different.
- Many rubrics give points for **"completeness"** or **"feasibility"**. → A deployed URL and a clean README earn these cheaply.
- Ties are broken by **memorability**. → One striking number, one visual moment, one product name that's easy to say.

## The 10 most common reasons finished projects don't win
1. Built the same idea as 10 other teams.
2. Demo depends on Wi-Fi / an API key and fails live.
3. The impressive part is hidden behind login or 6 clicks.
4. No clear user — "for everyone".
5. Explaining the tech stack instead of the problem.
6. Claims that aren't true (fake data presented as real, "AI" that isn't).
7. Ran out of time polishing a feature nobody saw in the demo.
8. No README / repo is messy / submission rushed at the last minute.
9. Pitch runs over time and gets cut before the wow.
10. Ignored the sponsor tracks — free extra chances to win.

## Points-per-hour rule (last 4 hours)
Rank possible fixes by (expected score gain × criterion weight) ÷ hours. Pitch and demo-reliability fixes usually beat new features.

## Standard tough questions to prepare
1. Is this data real? 2. What part is actually AI? 3. Doesn't <existing app> already do this? 4. How does it scale / what does it cost? 5. Privacy and misuse? 6. Who pays / how does it reach users? 7. What would you build next with a month?
